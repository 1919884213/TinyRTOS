# 为什么 `SVC_Handler` 和 `PendSV_restore` 的恢复代码一模一样？

你的观察完全正确——`SVC_Handler` 的后半段（恢复序列）和 `PendSV_restore` 就是**一模一样的代码**。这不是巧合，而是两者的本质就是同一件事。分几点说透：

---

## 1. 两段代码做的事完全相同：从栈恢复任务 + 切 PSP + 异常返回

对比 `Core/User/rtos/switch.s` 中的两段：

```asm
; ===== PendSV_restore（第 41~46 行） =====
    LDR     R1, =current_tcb     ; 取 TCB 地址
    LDR     R1, [R1]             ; 取 TCB 指针
    LDR     R0, [R1, #0]         ; 取 sp（TCB 第 0 成员）
    LDMIA   R0!, {R4-R11}        ; 弹软件压的 8 字
    MSR     PSP, R0              ; PSP 指向硬件压栈区
    BX      LR                   ; 异常返回，硬件自动弹 xPSR/PC/LR/R12/R3-R0
```

```asm
; ===== SVC_Handler（第 59~64 行） =====
    LDR     R0, =current_tcb
    LDR     R0, [R0]             ; R0 = current_tcb（os_start 已预选）
    LDR     R0, [R0, #0]         ; R0 = current_tcb->sp（首任务栈）
    LDMIA   R0!, {R4-R11}        ; 弹首帧软件 8 字
    MSR     PSP, R0              ; PSP = 首帧硬件区
    BX      LR                   ; 异常返回：弹硬件 8 字 → 任务从入口开跑
```

任务切换的"恢复"工作只有这些，因为剩下的 8 个寄存器（xPSR, PC, LR, R12, R3-R0）是由硬件根据 `EXC_RETURN` 自动弹出的。**软件只需要负责把 R4-R11 和 PSP 准备好**，其余全交给硬件。

---

## 2. 首次启动 = 一次"伪造的中断返回"

`os_task_create` 在创建任务时，就在任务栈里预先伪造了一个"刚被中断打断"的完整 16 字帧：

```
栈底（高地址）             （低地址）栈顶
┌─────────────────────┐
│ xPSR = 0x01000000   │ ← 硬件自动弹
│ PC   = 任务入口函数   │ ← 任务从哪开始跑
│ LR   = 任务退出钩子   │ ← 任务 return 后去哪
│ R12                 │
│ R3                  │
│ R2                  │
│ R1                  │
│ R0                  │
├─────────────────────┤
│ R11                 │ ← 软件手动弹
│ R10                 │
│ R9                  │
│ R8                  │
│ R7                  │
│ R6                  │
│ R5                  │
│ R4                  │
└─────────────────────┘
```

所以启动第一个任务，本质上就是"**假装从一个中断里返回**"。恢复格式与 PendSV 切换时的帧格式**完全一致**——这也决定了 SVC 必须写成和 PendSV_restore 一模一样，否则换帧格式约定就矛盾了。

---

## 3. SVC 只是 PendSV_Handler 的"下半场"

`PendSV_Handler` 做三件事：

| 阶段 | 动作 | 代码 |
|---|---|---|
| **上半场** | 保存旧任务（STMDB 压 R4-R11 存回 `current_tcb->sp`） | 第 24~32 行 |
| **中场** | 调度选新（`os_schedule` 更新 `current_tcb`） | 第 36~38 行 |
| **下半场** | 恢复新任务（弹帧 + 切 PSP + BX LR） | 第 41~46 行（即 `PendSV_restore`） |

而 `SVC_Handler` **只做下半场**，因为启动时：

- **没有旧任务可保存**：第一个任务之前，跑的 main/启动代码在 MSP 上，根本没有任务上下文存在 PSP 上需要保护；
- **不需要调度**：`os_start` 已经把第一个任务写进 `current_tcb`，SVC 只需照着它恢复。

### 对比表

| | `PendSV_restore` | `SVC_Handler` |
|---|---|---|
| 取 TCB | R1 中转（R1→[R1]→R1→R0） | 直接用 R0 |
| 调用 `os_schedule` | ✅ | ❌（`os_start` 已预选） |
| 恢复帧 + 切 PSP + BX LR | ✅ | ✅ |

去掉 `PUSH/POP {LR}` 和 `BL os_schedule` 后，SVC 就是 PendSV_restore 的**完整骨架**。

---

## 4. 一个有趣的细节：SVC 进异常时硬件在 MSP 压的那 8 个字去哪了？

SVC 触发时，CPU 把**当前 MSP** 上的 R0-R3, R12, LR, PC, xPSR 压了栈。但在 SVC 里 `MSR PSP, R0` 之后，`BX LR` 返回时 `EXC_RETURN`（返回 PSP 模式）会让硬件**从 PSP 弹帧**——也就是说：

> SVC 进入时压到 MSP 的那 8 个字**永远不会被弹出**，直接被丢弃。

这正是"接管"的含义：**启动现场被整个抛弃，换上新任务自带的假现场**。

---

## 5. 追问：PC 为什么要存入口函数？

看 `kernel.c` 的 `stack_init`：

```c
*--sp = 0x01000000u;              /* xPSR：bit24=T 位，必须 1（Thumb）漏了 HardFault */
*--sp = ((uint32_t)entry) | 1u;   /* PC：任务入口地址，OR 1 强制 Thumb 位（bit0=1） */
*--sp = 0u;                       /* LR：任务不返回 */
```

### 5.1 异常返回时，硬件会"自动跳转"到 PC

Cortex-M 的异常返回（`BX LR`）时，硬件从栈帧里依次弹出 8 个字，其中 **PC 被直接写入程序计数器**——CPU 立刻跳到这个地址开始取指执行。

所以栈帧里的 PC 就是"**任务恢复后从哪条指令继续跑**"的答案。

### 5.2 对老任务：PC = 被打断的位置

任务被 PendSV 切走时，硬件自动压栈的 PC 是**任务正在执行的那条指令的下一条**。等下次恢复，硬件弹出这个 PC，任务就"无缝续跑"。

### 5.3 对首任务：没有"被打断的位置"，就用入口函数代替

新任务**从来没运行过**，不存在"被打断的现场"。但启动机制是"伪造一次中断返回"——硬件不管你是真被打断还是假被打断，它只认栈帧里的 PC。

于是 `stack_init` 把 PC 填成 `entry`（任务入口函数地址）：

> 硬件一弹 PC → CPU 跳到 `entry` → 任务函数开始执行

这就是"**PC 存入口函数**"的全部意义：**让 CPU 第一次"返回"时，恰好落在任务的起点**。

### 5.4 为什么还要 `| 1u`？

Cortex-M 只支持 Thumb 指令，地址 bit0 必须是 1（Thumb 标志）。函数指针 `entry` 本身 bit0 通常已经是 1（编译器保证），但显式 `| 1u` 是**防御性写法**——万一地址被对齐过，也能强制 Thumb 位，避免跳进去 HardFault。

### 5.5 对照：LR 为什么存 0？

栈帧里 LR 是"任务 return 时跳去哪"。任务函数是 `void (*)(void*)`，正常永不返回；万一它 return 了，LR=0 会直接 HardFault——这反而是**故意的**：任务不该结束，结束就是 bug，立刻暴露。

---

## 6. 深层含义：为什么"必须"一样

栈帧格式是**全系统任务公用的协议**。将来如果给 Cortex-M4 加 FPU（需要额外保存/恢复 S16-S31），或者调整帧布局，`SVC_Handler` 和 `PendSV_restore` 必须**同步修改**，否则：

- 第一个任务启动用的帧格式 ≠ 后续任务切换用的帧格式
- 直接踩坏栈，任务跑飞

FreeRTOS 也是同样结构（`xPortStartFirstTask` 与切换路径共用同一套 `vPortRestoreContext`），这就是业界标准的启动方式。

---

## 一句话总结

> **`SVC_Handler` 就是 `PendSV_restore` 在"第一个任务"这个特例上的第一次执行**——没有上半场（无需保存旧任务），没有调度（已预选），只剩下半场的恢复动作，所以代码自然一字不差。

| 问题 | 答案 |
|---|---|
| PC 在栈帧里是什么角色？ | 异常返回时硬件把它写入程序计数器，决定 CPU 从哪继续执行 |
| 老任务恢复时 PC 是什么？ | 被打断位置的下一条指令（硬件自动压的） |
| 首任务启动时 PC 是什么？ | 任务入口函数 `entry`（`stack_init` 伪造的） |
| 为什么能这么干？ | 启动 = 伪造中断返回，硬件只认栈帧里的 PC，不关心真假 |
| 为什么 `\| 1u`？ | Cortex-M 必须 Thumb 模式，bit0=1 是 Thumb 标志，防止 HardFault |
| LR 为什么存 0？ | 任务永不返回，return 就 HardFault，故意暴露 bug |
